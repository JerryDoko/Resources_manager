# Hikari 下载来源信息

Resources Manager 可读取与媒体文件放在同一目录的 `hikari-source-<24 位小写十六进制 ID>.json`。支持 `kind: "hikari-download"`、`schema_version: 1`；不需要额外安装插件或修改数据库结构。

## 使用

1. 在 Hikari 完成下载后，保留下载文件夹里的来源 JSON。下载未完成时也可以导入已经完成的媒体。
2. 在 Resources Manager 对应的照片、漫画、条漫、视频或小说导入页添加文件夹。已导入过的文件夹点击「重新扫描」即可补入来源信息，不会重复建媒体项。
3. 打开文件夹详情，单击文件，在左侧详情查看「下载来源」：显示网站、原始 URL、来源标题、作者、标签和下载状态。「打开来源」仅在手动点击时打开 HTTP / HTTPS 网页。
4. 照片、漫画和条漫文件夹再次打开时会同步已有来源信息，并补入新图片；手动分组只更新已经归入该组的文件，不自动把同目录其他文件收入手动分组。

资源标签和来源标签按原著、角色、标签、作者分类，空分类不显示，每类默认最多 5 个。`parody:` / `copyright:` 对应原著，`character:` 对应角色，`artist:` / `author:` 对应作者，其他标签归入标签；未知前缀保留原名。查看分类不会改写原标签名称。详情页「查看全部标签」只展开当前系列已有标签，不显示库中其他系列的未关联标签。「添加 / 更改标签」可搜索并勾选资源库标签，保存时才修改关联。

## 合并规则

- 只按 `files[].path` 匹配具体文件，不把同目录所有来源分配给每个文件。同一文件可以关联多个来源，按 `source_id` 去重。
- `files[].source_url` 和 `title` 优先于根层；作者、标签合并根层及文件层信息，包含 `user_tags`。
- 只将匹配文件的标签追加到文件当前所属系列，不提供逐图片标签。不删除用户已设标签，重复扫描不产生重复关联。
- 来源记录保存在媒体项的 `metadata.hikari.sources`，保留原 metadata 中的播放、小说偏好及其他字段；不以下载器标题替换用户标题，不用下载百分比修改阅读进度，不修改评分或自定义封面。
- 下载状态只是下载任务状态。`completed` 表示下载器报告已完成，其余状态不代表资源管理器已看完；下载数量未知不影响已完成文件导入。
- JSON 使用相对路径，文件夹整体移动后，重新导入到新库仍可恢复来源。已有库仍按媒体绝对路径去重，不会自动迁移旧路径或还原旧观看进度。
- 不回写来源 JSON，不访问来源或 CDN，不读取下载 Cookie、代理设置或 `.hikari-state`。没有来源 JSON 或没有匹配记录时，媒体照常导入。

## 安全与排错

- 单个 JSON 最大 16 MiB；坏 JSON、未知版本、文件名与 `source_id` 不一致、符号链接来源 JSON 会被跳过，不阻断媒体扫描。
- 文件路径不能是绝对路径、Windows 盘符路径或包含 `..`。文件必须存在且为普通文件；真实路径不得通过符号链接跳出 JSON 所在目录。`.part`、`.ytdl` 不作为来源记录的完成文件。
- 每次扫描只解析每个媒体父目录一次。下载器更新 JSON 后，再次扫描或重新打开图片文件夹即可读取新状态。
- 只读取媒体父目录中的来源 JSON。把 JSON 留在下载器生成的位置，不要移到统一的上级目录。
- 如果没有显示来源，先检查 JSON 的文件名、版本、文件清单和文件位置；旧下载缺失的标签不会被自动推断。
- 如果旧媒体的 metadata 已损坏或不是 JSON 对象，导入器不会覆盖它来写入来源；需要先通过备份排查原数据。

## 验证

运行 `npm run test:scanner`，覆盖所有媒体扫描分支、已有项重新扫描、图片增量同步、多来源目录、移动后重建、旧标签关联表、无效输入与路径边界，以及用户信息保留。桌面回归可运行 `node scripts/test-hikari-desktop.mjs`，使用隔离临时书库，不读取或修改个人资源库。
